# Mini branch migration proposal

Parent: https://github.com/glitchwerks/mini-backlog.md/issues/14. Status: proposed; permanent upstream/mini branches, default-branch changes and ruleset activation remain unapplied. Runtime tooling and the reviewed baseline integrated into `main` through PR #19 at `5e38dda16be939bfb21872592c068680cef21a85`. Issue #14 explicitly requires a concrete migration decision first.

## Decision to review

Create a clean permanent `upstream` mirror and a permanent `mini` integration branch, make `mini` the default, and keep the current `main` history intact as a compatibility branch. Prepare sync candidates in disposable branches and review the runtime reports before integration. This is the recommended additive migration because #14 requires preserving mini history, upstream ancestry, existing tags and source-only distribution; current refs are captured in `docs/surfaces/branch-migration-inventory.json:L1-L121`.

Merge direction determines which checked-out branch receives the result. Mini changes belong in a temporary candidate or the permanent mini branch. Merging mini into the permanent upstream mirror would make that mirror include mini changes. Either candidate construction direction can preserve both histories; branch names alone do not reduce conflicts. Source: https://git-scm.com/docs/git-merge (fetched 2026-10-03), description and true-merge sections; issue #14.

## Future sync procedure

Use an isolated worktree on `codex/sync-upstream-v<version>` created from `mini`. Merge the selected upstream commit with a retained merge commit. Capture real old/new upstream executables, build the candidate and run the three comparisons documented in `docs/surfaces/README.md`. Review conflicts against the documented restricted surface and fix them on the candidate. Integrate through a PR targeting `mini` using a merge commit after all required checks and review feedback are resolved. Update the clean `upstream` mirror to the selected upstream commit separately. Source: issues #12–#14, PR #9, `README.md:L97-L111`, Git merge source cited above.

An upstream-first candidate is also valid: start from the selected upstream commit and merge `mini` into that disposable candidate, as in the demonstration. Review exactly the same reports and target `mini` for integration. The permanent upstream mirror receives only upstream source. This contains mini policy changes in the candidate and mini integration destination. Source: issue #14; the retained demonstration merge and runtime report.

Release from integrated `mini` using the existing validation and `mini-v<upstream-version>` source tags. Keep source builds and automatic source archives; do not add publishing or binary release assets. Source: issue #3 / PR #4 and `DEVELOPMENT.md:L170-L191`.

## Rollback

If default-branch installation or contribution routing fails, restore default `main`, restore the recorded affected PR bases and revert only the migration PR's CI/README/DEVELOPMENT changes through a PR. The additive migration leaves original main/tag history available. If the new repository ruleset blocks valid PRs, disable that specific newly recorded ruleset ID and inspect the failed/missing context; preserve organization ruleset `15682536`. Do not force-push main, rewrite tags or delete mini/upstream to perform rollback. Retain new branches until active work is reconciled. Sources: issue #14, current inventory, GitHub default-branch and ruleset docs cited above.
